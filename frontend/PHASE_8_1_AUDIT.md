## 1. The 8 Business-Control Dimensions

For every business object and API endpoint in the QStudy Agent Portal, we evaluate:
1. **Owner:** Which actor originates and is legally/contractually accountable for this record?
2. **Reader:** Who is authorized to inspect this information?
3. **Creator:** Who is authorized to instantiate this record?
4. **Modifier:** Who is authorized to edit mutable attributes?
5. **Approver:** Who has the institutional authority to validate and advance state?
6. **Rejector:** Who has the authority to deny, flag, or demand corrections?
7. **Transition Driver:** What business event causes progression to the next lifecycle stage?
8. **Financial Consequence:** What liability, commission trigger, or settlement is generated by this transition?

## 2. Cross-Module Ownership & Causality Matrix

### Module 1: Student Referral & Profile
- **Owner:** Agent (or Admin on behalf of institution).
- **Reader:** Owning Agent (Self records only); Admin (All students).
- **Creator:** Agent (Registers prospective candidate); Admin.
- **Modifier:** Owning Agent (Pre-verification only); Admin.
- **Approver:** Verification Officer / Admin (Sets `verificationStatus = 'Verified'`).
- **Rejector:** Verification Officer / Admin (Flags missing data or sets `Rejected`).
- **Transition Driver:** Referral $\rightarrow$ Initial contact $\rightarrow$ Document submission $\rightarrow$ Institutional verification.
- **Financial Consequence:** None directly. Verifying a student is a *prerequisite* for invoice eligibility, but does not itself create monetary liability.
- **Identified Flaws in Current Code:**
  - `GET /api/agents` leaks all agency competitor identities and contact details to any logged-in agent.
  - `DataContext.js` fallback mock data leaks students across different agents.
  - `StudentDetailsPage.jsx` has client-side fallback `students.find(s => s.id === id)` if API returns an error, bypassing backend 403 enforcement.

---

### Module 2: Student Documents
- **Owner:** Student (subject) / Agent (uploader).
- **Reader:** Owning Agent; Verification Officer / Admin.
- **Creator (Uploader):** Owning Agent; Admin.
- **Modifier:** Owning Agent (Re-uploading corrected document); Admin.
- **Approver:** Admin / Verification Officer (Sets document `status = 'approved'`).
- **Rejector:** Admin / Verification Officer (Sets document `status = 'rejected'` or `'correction_required'` with remarks).
- **Transition Driver:** Document upload $\rightarrow$ Review queue $\rightarrow$ Per-document verification/rejection $\rightarrow$ Re-submission if rejected.
- **Financial Consequence:** Documents validate student identity and eligibility. Fraudulent or unverified documents passing through lead to illegitimate commission claims.
- **Identified Flaws in Current Code:**
  - Documents stored as unstructured JSON array on the Student model without distinct per-document lifecycle status in the UI.
  - When an admin rejects a student or document, the Agent portal lacks an actionable "Correction Required" prompt with the verifier's feedback.

---

### Module 3: University & Course Catalog
- **Owner:** University Partner / QStudy Admin.
- **Reader:** All authenticated users (Agents & Admins).
- **Creator:** Admin only.
- **Modifier:** Admin only.
- **Approver:** Admin only.
- **Rejector:** Admin only.
- **Transition Driver:** Partner onboarding $\rightarrow$ Active in catalog $\rightarrow$ Inactive/Decommissioned.
- **Financial Consequence:** Dictates authoritative course tuition and baseline commission rates.
- **Identified Flaws in Current Code:**
  - `GET /api/universities/:id` leaks global application counts (`result.applicationCount = applicationCount`) to agents.
  - `UniversityDetailsPage.jsx` associated applications table lacked strict agent filtering.

---

### Module 4: Application Lifecycle
- **Owner:** Owning Agent (Applicant representative).
- **Reader:** Owning Agent; University Admissions / Admin.
- **Creator:** Owning Agent (Drafts & submits application for their student).
- **Modifier:** Owning Agent (in `Draft` status only); Admin (during review/processing).
- **Approver:** Admin / Admissions (Advances from `Submitted` to `UnderReview` $\rightarrow$ `OfferReceived`).
- **Rejector:** University / Admin (Marks `Rejected` with reason).
- **Transition Driver:** Student application submission $\rightarrow$ Document vetting $\rightarrow$ University assessment $\rightarrow$ Offer issued.
- **Financial Consequence:** Records program choice and tuition baseline.
- **Identified Flaws in Current Code:**
  - `Estimated Tuition Fee` is a freeform, unverified input in `ApplicationModal.jsx` rather than pulling authoritatively from `Course.tuitionFee`.

---

### Module 5: Admission Milestones (Campus Visit, Offer, Admission Confirmation, Deposit, Enrollment)
- **Owner:** University Admissions Team / QStudy Operations.
- **Reader:** Owning Agent (Informed/Read-only); Admin/Admissions/Finance (Full).
- **Creator:**
  - *Visit Request:* Agent may request visit.
  - *Visit Confirmation:* Admin/University confirms & marks completed.
  - *Offer Recording:* Admin/Admissions only.
  - *Admission Confirmation:* Admin/Admissions only.
  - *Tuition Deposit Verification:* Admin/Finance only.
  - *Enrollment Verification:* Admin/Admissions only.
- **Modifier:** Admin / Admissions / Finance.
- **Approver:** Admin / Admissions / Finance.
- **Rejector:** Admin / Admissions (Revoked offer / Cancelled admission).
- **Transition Driver:** Official institutional communication (CAS/I-20 issuance, bank wire/payment gateway confirmation, student campus arrival).
- **Financial Consequence:** **HIGH.** Completing `AdmissionConfirmed` + `Deposit Verified` + `Enrolled` flips `isInvoiceEligible = true`, immediately creating commission entitlement.
- **Identified Flaws in Current Code:**
  - **P0 Conflict of Interest:** Agents can call `POST /api/applications/:id/admission`, `PATCH /api/applications/:id/deposit`, and `POST /api/applications/:id/enrollment` directly on their own applications, unilaterally triggering commission eligibility.

---

### Module 6: Invoices
- **Owner:** Agent (Creditor / Claimant).
- **Reader:** Owning Agent; Finance Team; Admin.
- **Creator:** Owning Agent (once application is verified and eligible); Admin.
- **Modifier:** Agent (Draft/Pending only); Finance.
- **Approver:** Finance Team (`FinanceReviewModal`).
- **Rejector:** Finance Team (Rejection with mandatory reason and dispute remarks).
- **Transition Driver:** Verified student enrollment $\rightarrow$ Agent generates invoice $\rightarrow$ Finance review queue $\rightarrow$ Approved / Rejected.
- **Financial Consequence:** **DIRECT MONETARY LIABILITY.** Approved invoice commits QStudy / University funds for payout.
- **Identified Flaws in Current Code:**
  - Invoice generation allows invoice creation against applications whose admission/deposit was self-confirmed by the agent.
  - Calculation falls back to synthetic `$10,000` tuition if `app.tuitionFee` is blank.

---

### Module 7: Finance Review & Payoffs
- **Owner:** QStudy Finance Department.
- **Reader:** Finance Team; Admin; Owning Agent (Settlement summary & receipt only).
- **Creator (Payoff Settlement):** Finance Officer.
- **Modifier:** Finance Officer.
- **Approver:** Senior Finance Manager / Executive Admin.
- **Rejector:** Finance Team.
- **Transition Driver:** Invoice Approved $\rightarrow$ Scheduled in Payoff Batch $\rightarrow$ Disbursement via bank wire / gateway $\rightarrow$ Settled.
- **Financial Consequence:** Capital disbursement. Bank transaction reference recorded.
- **Identified Flaws in Current Code:**
  - Payoff settlement modal and payout action does not enforce Finance role restriction on the backend (`admin` was lumped together without role segregation).

## 3. Strict Execution Plan: Phase 8.1-A (Agent Isolation & Security)

### Objectives
1. **Universal Agent Data Isolation:** Under no circumstances may an agent query, infer, or view another agent's students, applications, invoices, or agency profile data.
2. **Purge Information Leaks:**
   - Restrict `GET /api/agents` and `GET /api/agents/:id` strictly to `admin` / `finance`. Agents must only access `GET /api/agents/me` or their own profile.
   - Restrict `EventDetailsPage.jsx` and `eventController.js` to ensure candidate rosters only show the agent's own candidates, and event capacity calculation does not confuse personal candidates with total event attendance.
   - Fix `universityService.js`: Scoped `applicationCount` in `GET /api/universities/:id` so agents only see their agency's application count (or aggregate strictly without cross-agent detail).
   - In `DataContext.js`: Eliminate multi-agent mock fallback bleed. Ensure all cached student/application filtering strictly enforces `currentUser.id`.
   - In `StudentDetailsPage.jsx`: Remove client-side fallback cache searching when an API call fails or returns 403/404. Render a clean 403 Forbidden / 404 Not Found error state.

## 4. Verification Protocol for Phase 8.1-A
1. **Automated API Security Penetration Test Suite:**
   - Agent A attempts to fetch Agent B's student by ID $\rightarrow$ `403 Forbidden`.
   - Agent A attempts to fetch Agent B's application by ID $\rightarrow$ `403 Forbidden`.
   - Agent A hits `GET /api/agents` $\rightarrow$ `403 Forbidden`.
   - Agent A hits `GET /api/universities/:id/applications` $\rightarrow$ Receives only Agent A's applications.
   - Agent A hits `GET /api/events/:id` $\rightarrow$ No exposure of other assigned agents' private contact info.
2. **Frontend UI Smoke Test:**
   - Direct URL injection test: Agent manually navigates to `/agent/students/{agentB_studentId}` $\rightarrow$ Access denied UI shown, no data bleed.
   - University details page test: Agent only sees own application count.
3. **Production Build:** `npm run build` exit code 0.
